LocalWave Rust Port

Move LocalWave from SwiftUI to Rust on pxui, with libpxui built from a submodule and bundled inside the app, the same way Rays does it. This page says what fits today, what pxui has to gain first, and the order to do it in.

macOS look and motionReachable 1:1 after 11 pxui fixes
Design fitGood. Both are square, hairline, mono-data
pxui on iOSDoes not exist yet. It is its own project
Zero-alloc framesAlready a tested pxui contract

The short answer on theming: tokens, looks, state transitions, shadows, blur and canvas drawing cover most of the app. Theming alone is not enough for 1:1. The gaps are in animation curves, scale animation, text features and accessibility, and each one is a contained pxui change listed below.

How the app is put together

Rust owns every line of logic and UI. Apple frameworks that have no Rust equivalent (AVFoundation, MediaPlayer, security-scoped bookmarks, file coordination, ImageIO, pickers) stay behind one small Objective-C shim crate, the same pattern pxui uses for Metal in metal_sys.

lw_binEntry point. Owns the window, the Metal device and the frame loop. Links ogpu_metal and pxui_sdl statically, as Rays does.
lw_uiAll views: shell, Library, Player, Files, sheet/dialog/menu presenter, command palette, canvas drawings. Talks to pxui through the safe pxui wrapper.
libpxui.1.dylibShared library, built from pxui/ (submodule) by make lib. Lives in Contents/Frameworks, loaded through @rpath.
lw_coreModels, queue and shuffle, SQLite repositories and FTS5 search, import, FLAC tag parser, offline cache, preferences. No UI, no Apple calls.
lw_apple_sysObjective-C shim with a C header: queue player, audio session, Now Playing and remote commands, bookmarks, file coordinator and presenter, ImageIO thumbnails, tag reading, waveform PCM, pickers, share, appearance and reduce-motion signals.

Three things differ from the Rays script and must be added:

  • Sandbox and entitlements. LocalWave's Mac app is sandboxed (app-sandbox, files.user-selected.read-only, files.bookmarks.app-scope). The bundle script has to sign with --entitlements and embed a provisioning profile for TestFlight. Rays signs for Developer ID only.
  • Same bundle id. Keep com.olegpustovit.localwave and the same team, so the container, the database, the preferences and the stored bookmarks carry over without a migration.
  • SDL3 inside the bundle. The Rays script already copies non-system dylibs into Frameworks. For a sandboxed store build, link SDL3 statically instead so only libpxui ships as a dylib.

Where 1:1 has a hard edge

  • Glyph rendering. pxui rasterizes with swash, SwiftUI with CoreText. Layout can match to the pixel because both read the same font tables, and the app already forces explicit line boxes. The antialiasing of individual glyphs will differ slightly. The existing Chromium reference tests (19 baselines, 1/64 pt label widths) become the acceptance test for the text stack.
  • Native pieces that go away. The macOS right-click menu becomes the app's own panel (already built for the menu button). Alerts become the app's own dialog. The system audio-route button on iOS has to stay a native view placed over the canvas.
  • Input latency. pxui delivers input one frame late by design. At 120 Hz that is 8 ms on scrubbing and swipes. Measure it on device before accepting.

pxui on iOS

There is no iOS code in pxui today: no target cfg, no touch events, no host. The engine core is platform-free and the Metal shim only uses frameworks that exist on iOS, so this is a port, not a rewrite. It should be developed and proven inside pxui with the gallery app before LocalWave depends on it.

What has to feel like iOS

None of this comes from the host. A custom-drawn UI gets no system scrolling or navigation from either SDL3 or UIKit, so pxui has to reproduce each behaviour and the P6 gate checks them side by side with the current app on a device.

BehaviourTarget
Scroll decelerationMatch UIScrollView's normal rate (velocity × 0.998 per ms). Compare travel distance for the same flick, within a few points.
Rubber-band at the edgesSystem resistance curve (constant 0.55) and spring-back. Pull to refresh hangs off the same overscroll.
Touch-down while coastingStops the scroll at once and does not register as a tap on the row.
Tap versus scrollRow highlight is delayed until the touch is known not to be a scroll; about 10 pt of slop.
Edge-swipe backInteractive: the page follows the finger from the left edge and completes or cancels on release velocity. Today this is the one thing the app borrows from NavigationStack.

KeyboardDialogs move with the keyboard on the system's own curve and duration, not after it.

Text editingAutocorrect off where the app sets it, Done key, dictation and marked text for CJK input. No magnifier loupe; fields are single-line names and search.

Port sequence

macOS first, because pxui already runs there and the Mac app is the smaller surface. The SwiftUI app keeps shipping until each platform's Rust build passes its gate.

P0

Scaffold and bundle

Add the submodule, workspace, Makefile and bundle script. Ship an empty pxui window as a signed, sandboxed LocalWave.app. Delete localwave-tui, its SwiftPM target and the SwiftTUI dependency, and update AGENTS.md.

Gate: otool -L shows @rpath/libpxui.1.dylib; codesign --verify --deep --strict passes; the app launches from /Applications.

P1

Core in Rust, no UI

Port Domain and Data (about 4,000 lines of Swift): models, queue and shuffle, SQLite repositories, FTS5 search with BM25, import, FLAC parser, offline cache. Open the existing musicApp29.sqlite as is, with the system SQLite. Port the 18 SwiftPM data test files to cargo t.

Gate: Rust and Swift read each other's database; songKey and pathId are byte-identical on a fixture library; cargo t under 30 s.

P2

Apple shim and playback

Write lw_apple_sys. Port the player view model (about 1,500 lines) to a Rust state machine driving the queue player through the shim. A headless binary plays a queue.

Gate: gapless pre-queue of 2 items, Now Playing and media keys, interruption handling, bookmarks from the Swift app still resolve.

P3

pxui fixes 1 to 10

Runs alongside P1 and P2, in the pxui repository.

Gate: each fix has a golden or allocator test in pxui; the gallery shows the LocalWave theme.

P4

macOS UI

In this order: theme files and motion tokens, shell (sidebar, transport, Now panel), song table and album grid, player and queue, Files and settings, presenter (sheet, dialog, menu, palette, toast), keyboard shortcuts, drag and drop. About 15,000 lines of SwiftUI to replace.

Gate: pxui goldens against the existing 1440×872 reference canvases; every shortcut in the current table works; 10,000-song library meets the budgets below.

P5

Ship macOS

TestFlight build from the bundle script, replace build-mac-dmg.sh and the CI release job. Remove the SwiftUI Mac target.

Gate: one release cycle on TestFlight with no regressions reported.

P6

pxui on iOS

The table above, proven with the pxui gallery on a device and in the simulator.

Gate: gallery scrolls at 120 Hz on device with zero warm-frame allocations; text field with keyboard works; every row of the iOS feel table passes next to the SwiftUI app.

P7

iOS UI and ship

Narrow layout: nav deck, mini-player, bottom sheets, swipe rows, long-press menus with the blurred backdrop, pull to refresh, pickers and share through the shim. Background audio check on device.

Gate: goldens against the 390×778 reference canvases; device qualification for playback, bookmark recovery and cloud files. Then delete the Xcode project and the Swift sources.

Performance rules for the app

pxui already asserts zero allocations on a warm frame with a counting allocator. The app has to keep that property, so these are written as tests, not intentions.

RuleHow it is enforced
0 allocations per warm frameA mem_sys counter test scrolls a 10,000-song table, scrubs the waveform and opens a menu. Any allocation fails the test.
Frame build under 1 ms at 10,000 songsFixed-height virtualized rows. pxui's recorded cost is about 240 µs for 500 rebuilt widgets on an M1.
No frames when idle; only dirty layers while playingThe transport clock and equalizer sit in their own view so the table is skipped by revision. Assert the idle frame count is 0.
No per-frame string buildingSong text lives in one arena per library load and rows borrow from it. Times and counts format into stack buffers with cfmt.
Column widths measured onceToday SwiftUI re-measures and re-sorts the whole array on each render. Measure on data change and cache.
Artwork never decodes on the UI threadWorker thread decodes through ImageIO; a fixed-capacity LRU of textures replaces today's decode-on-every-appear.
Worker to UI messages without allocationPreallocated ring buffer plus a host wake. Database and import work stay off the UI thread; pxui itself is single-threaded.

Decisions

  • Objective-C shim: accepted. Apple framework calls live in lw_apple_sys.
  • Terminal player: removed in P0.
  • iOS host: SDL3.
  • Accessibility bridges: deferred on macOS and iOS. The Rust app will be a VoiceOver regression from the SwiftUI app until they land.
  • Still open: how strict 1:1 is on glyph antialiasing. Layout parity is testable and planned. Matching CoreText's rasterization exactly would mean a CoreText rasterizer inside pxui.

Not verified

  • Nothing was built or run. pxui findings come from reading the source at 59d6f45; the LocalWave inventory from reading the Swift sources.
  • Whether cosmic-text 0.19 selects weights on Host Grotesk's variable axis, and how it exposes OpenType features. Both decide the size of fixes 5 and 8.
  • Whether sdl3_sys's build script can target iOS (it finds SDL through Homebrew today), and how SDL 3.4 behaves on iOS for keyboard frame reporting, marked text and 120 Hz pacing. The P6 spike answers these.
  • That stored bookmarks and a path-opened SQLite database behave identically under the sandbox when the picker is SDL's instead of SwiftUI's.
  • There is no measured performance baseline for the current app at large library sizes, so "as fast as today" has no number yet.
