pxui Unification Plan

v3 · 17 Nov 2026 · base LocalWave fb16eaa (rust-port) · pxui d6b4182b (ABI 1.72) · reference spec: pxui API Redesign + docs/dx-checkpoint/api_spec.md · replaces every open DX row · v3 folds in two rounds of independent review (coverage and soundness: 57 findings, then 21 more)

In one paragraph. One implementer (an Opus subagent) works through twelve packages, one at a time, never in parallel. The orchestrator (Claude, main session) writes each brief, stops the implementer at fixed review points, reviews every diff against the ledger (§5) and the checklist (§13), and lands the work. Order: reset and measure (U0) → make the existing pxui surface one shape per job (U1a–c) → finish the widget set and map every LocalWave site to its final call (U2a–b) → LocalWave looks, literals and keys (U3) → move every LocalWave control onto its pxui widget with registered bodies (U4a–b) → cut ABI 2.0 (U5a–b) → documentation and freeze (U6). Each call gets its final signature in exactly one step, and each LocalWave site is touched once. Zero warm allocations, frame budgets and build speed are measured at CP0, CP1 and CP2 plus four narrow targeted runs, and must not regress. Wide mechanical edits are codemod scripts. Every outstanding finding has one destination in §11.

Owner sign-off (approved 17 Nov 2026). U0.6 writes these into AGENTS.md and pxui/AGENTS.md:

No Swift work. The Swift app is no longer developed. No Swift/Xcode checks run in this plan, and AGENTS.md's Swift sections are marked historical in U0.6.

Commit checks. Each commit runs targeted Tier A. The bounded suite and make check run at the end of each package and at checkpoints. Review fixes are separate [U<N>.<k> fix] commits, and the orchestrator's [U<N>] status commit counts as part of the step it records. The freeze (U6.7) reuses CP2's numbers, with mechanical evidence that runtime code is unchanged; this replaces the usual PERF run for that step.

Pointers. A u<N> branch may record pointers to unpublished pxui u<N> commits. At landing, pxui is pushed first and checked as fetchable before LocalWave is pushed.

Build-time meter. tools/dx/buildtime.sh may use its own target directories, clean builds and a temporary worktree.

Breaking changes are welcome. No compatibility layers or deprecation periods, in the Rust API or the C ABI. The target is a solid end state, and the only constraints are performance, build speed and zero allocations. pxui/AGENTS.md's "additive changes only" rule is lifted until the 2.0 freeze.

D25Locked call shape (after comparing SwiftUI, gpui, rune; §5c)

Keyless layout containers. row/column/stack(Node, f) take no key; their identity is position among siblings, as labels already work. ui.id(key, f) keys a subtree where identity must survive siblings appearing or disappearing (conditional or animated content), like gpui's .id() and rune's .key(). Interactive widgets, node, view_of and list rows stay key-first.

Inline style values allowed. Name a const when a style is reused. A one-off style or runtime field (&BUTTON.disabled(!ok), Node::row().gap(8.0)) may be written inline. These are Copy stack values with no allocation and no generics; struct literals stay banned.

App-owned collection state. ListState holds selection and anchor. TableState holds widths, sort and selection. Each is passed as one &mut instead of three parameters.

PickResponse.chosen_id: Option<i64>: the chosen Segment.id, so the app maps straight to its enum.

Style scope = ui.themed. A subtree-wide style is a derived ThemeHandle that sets <kind>.body/variant and looks; there is no new call. SwiftUI's environment covers this; gpui and rune style per element.

One name per widget. button(key, text, &Button) and toggle(key, text, on, &Toggle). The _with forms and the keyless short forms are deleted, like gpui's Button::new(id, label) and rune-kit's Button::new("Save"). This departs from the reference spec's button_with/toggle_with, deliberately.

.disabled(bool) on every style value, replacing .enabled(bool), to match ui.disabled(..), SwiftUI and gpui.

Kept on purpose.

 Results are returned (Response), not handler closures. No closure is stored per frame, which keeps frames at zero allocations and the API non-generic.

 Styles are const values, not trait builders on elements.

 Structure comes from registered bodies, which reach C callers too.

5. The API ledger: one public UI

The target public surface. Rule: a call not marked with a step keeps its HEAD signature exactly. A call marked with a step changes once, in that step, to the signature shown. U0.3 generates the full HEAD → ledger delta from tools/dx/surface.py, and every delta line must carry a step id here (otherwise it reverts to HEAD). K: Into<Key> and F: FnMut(..) are the one-line shells; &mut self is omitted.

Rules every row obeys

Style values are Copy, have DEFAULT and presets, const fn builders taking self; looks borrowed (Option<&'a States>) in every style value that has looks. No call site writes a struct literal. Reused styles are named consts; one-offs and runtime fields may be built inline (D25.2).

Labels are keyless leaves (text, Label). Interactive calls: key first, return Response (clicked, secondary, hovered, held, focused, activated, changed, handle) or one result struct. Runtime data (value, range, title, anchor, widths, selection) stays a parameter; style values hold only constants.

Sizes f32, positions Point. Result<_, Error> for fallible-by-data calls, Option for "absent", panics only for documented caller bugs.

Build-time setters (text, style, set_view) set state during the build; the patch_* family (patch_text, patch_look, patch_rect, patch_mark, patch_field) updates retained nodes without a rebuild. Both families are documented as such.

5b. Where it lands: case studies (reference)

Each case compares three versions of the same control:

Before: real LocalWave code at fb16eaa (trimmed, file:line given).

After: the same control at the end of the plan, written against the ledger. Builder names may shift slightly at the U1/U2 shape stops; the shape will not.

SwiftUI: the closest idiomatic equivalent.

All "after" code allocates nothing per frame: styles are const, item arrays live on the stack, and display strings come from the snapshot.

Errors are Results, not panics. There is one theme entry point, and key codes are typed. Theme files carry the tokens and the <kind>.body = localwave-… lines. Structural customisation is a registered body function, plain data in and nodes out, with no generics.

6. How LocalWave uses pxui (the end state)

Appearance = theme. Colour tokens in themes/app-{light,dark}.theme; every look a named const in crates/lw_ui/src/shell/theme.rs built from Rgba::token(..) (with .alpha(a) where Swift used opacity). No ui.color(X) in build paths except genuinely dynamic values listed in the allowlist (e.g. the run-time scrim at shell.rs:957). No struct literals of pxui types.

Structure = registered bodies + variants. Every distinctive control is the standard pxui call plus a localwave-* body selected by a theme line (<kind>.body) or .variant(n). Bodies are the only place raw nodes build interactive structure; they draw only from the config they receive.

Composite content (album cards, artist rows, mini player, compact song rows, play-queued body, source card) stays pressable + labels, allowlisted with the reason "composite".

Keys are static ids or item ids; styles are app consts; helpers that recreate a widget are deleted.

Gaps stop the step (gap protocol, §7). Never a workaround.

Gap protocol (U3–U4)

If a LocalWave site can't be expressed with the ledger, the implementer stops with GAP: file:line — what is missing. The orchestrator writes a gap step U2b.4.<n> and adds it to the ledger with that id. The same implementer builds it on the current u<N> branches (a pxui commit plus its LocalWave pointer commit). The orchestrator reviews it as a mini shape check (signature + docs + tests), then the package resumes. The gap step lands with the package, so nothing lands on rust-port mid-package and both branches stay fast-forwardable.

Commits

One step = one commit per repo; subject starts with the step id; LocalWave commits carry the pxui pointer; evidence (tests, counts, D9 diffs, build times) in the message. A large step may use several commits named [U1a.1/2], [U1a.1/3]…, each building.

ABI-changing pxui commits take the next minor and regenerate manifests (D17).

Main checkouts only, branch u<N>; no worktrees (except inside buildtime.sh --compare), no stash, one target dir, CARGO_BUILD_JOBS unset.

Scope

The step list is the scope. Other findings → the Found list. Refactor steps move code verbatim. Ponytail: smallest change that meets "done when"; an existing pxui function before a new one; nothing the step does not name.

9. Codemods

A change touching more than ~5 sites the same way is a script in tools/dx/codemods/ (stdlib Python), or rust-analyzer ssr for expression rewrites. ssr needs resolving code, so run it before changing the signature, in the workspace where the callers live.

Every script: --dry-run per-file counts; runs over pxui and LocalWave; prints the sites it skipped; committed in its step. Afterwards: compile, targeted tests, read the diff once, hand-edit the skipped sites.

Python rewriters use a small tokenizer that understands strings, char vs lifetime, and comments. Field → builder tables are written by hand (names are not 1:1: w vs w_px, axis → Node::row(), ..base spreads).

Manifests are never edited by scripts; gate -- abi-snapshot --write regenerates them. Never rustfmt pxui or pxui_types.

Starting points: tools/dx/codemods/archive/ (codemod_a…g, codemod_dx1.12c, codemod_dx3.22a.py, codemod_i.py, bc_closures.py, split_items.py, perftable.py).
